## 1 วัตถุประสงค์ของโมดูล

โมดูล Jar Test ใช้บันทึกการทดสอบหาปริมาณสารเคมีที่เหมาะสมสำหรับกระบวนการผลิตน้ำ ผู้ใช้เริ่มจากข้อมูลกิจการประปา แหล่งน้ำ สถานะการเดินระบบ และคุณสมบัติน้ำดิบ จากนั้นเลือกสารเคมี กำหนดความเข้มข้นของสารละลายตั้งต้น บันทึกอัตราจ่ายของ Jar จำนวน 6 ใบ กรอกผลคุณภาพน้ำ ตรวจผลผ่านหรือไม่ผ่านตาม Bound สรุปอัตราจ่ายที่เหมาะสม และปิดงานเพื่อป้องกันการแก้ไขต่อ

เอกสารนี้กำหนดเฉพาะพฤติกรรมของระบบเดิม ฟังก์ชันใหม่ การปรับ UX การทำ Bound ให้ผู้ใช้ตั้งค่าได้ และการออกแบบฐานข้อมูลสำหรับระบบใหม่อยู่นอกขอบเขตฉบับนี้

## 2 วิธีใช้เอกสารนี้

เอกสารนี้ใช้คำต่อไปนี้เพื่อบอกระดับความแน่นอนของข้อกำหนด

- **ยืนยันจากหน้าจอ** หมายถึงพบองค์ประกอบหรือพฤติกรรมในระบบเดิมโดยตรง
- **ยืนยันจากการทดสอบ** หมายถึงพิสูจน์ด้วยข้อมูลทดสอบในสถานีผลิต Head Office
- **ต้องยืนยันเพิ่ม** หมายถึงระบบเดิมแสดงผลลัพธ์ แต่ยังไม่ทราบค่าคงที่ สูตรย่อย หรือเงื่อนไขภายในที่แน่นอน

ผู้พัฒนาหรือ AI ที่นำเอกสารนี้ไปใช้ต้องไม่แต่งค่าที่ระบุว่า “ต้องยืนยันเพิ่ม” ขึ้นเอง หากจำเป็นต้องพัฒนาก่อน ให้แยกค่าเหล่านั้นเป็น configuration หรือ placeholder ที่ติดป้ายชัดเจน

## 4 ผู้ใช้งานและสิทธิ์

ระบบเดิมที่สำรวจอนุญาตให้ session ปัจจุบันเข้าถึงหน้ารายการ สร้าง ดู แก้ไขก่อนล็อก เลือกสาร สร้างรอบทดสอบ กรอกผล สรุปผล และปิดงานได้ ไม่พบหน้าปฏิเสธสิทธิ์ใน flow นี้

ข้อกำหนดการทำสำเนาระบบควรรองรับอย่างน้อยสองความสามารถเชิงตรรกะ แม้ชื่อ role จริงของระบบเดิมยังไม่ทราบ

| ความสามารถ | พฤติกรรม |
|---|---|
| อ่านข้อมูล | ดูรายการ ตัวกรอง รายละเอียด รอบทดสอบ ผล และสรุป |
| จัดการงาน | สร้าง แก้ไขก่อนล็อก เลือกสาร เพิ่มรอบ กรอกผล สรุป และปิดงาน |

ระบบเดิมมีปุ่มลบในหน้ารายการ แต่ไม่ได้ทดสอบการลบหรือ confirmation เพื่อหลีกเลี่ยงผลกระทบต่อข้อมูลจริง รายละเอียดสิทธิ์ลบและเงื่อนไขการลบจึงเป็นรายการที่ต้องยืนยันเพิ่ม

## 5 ภาพรวม User Flow

```text
หน้ารายการ
  -> สร้าง Jar Test
  -> บันทึกข้อมูลหลัก
  -> เปิดหน้ารายละเอียด
  -> เลือกสารเคมีและความเข้มข้น stock solution
  -> ยืนยันเข้าสู่ขั้นกำหนดอัตราจ่าย
  -> เพิ่มรอบทดสอบ
  -> กำหนด dose ของสารแต่ละชนิดใน Jar 1 ถึง Jar 6
  -> ระบบคำนวณปริมาณสารละลายและต้นทุน
  -> กรอกผลคุณภาพน้ำของ Jar 1 ถึง Jar 6
  -> ระบบประเมินผ่านหรือไม่ผ่านด้วย Bound
  -> เลือกหรือยืนยัน Jar ที่ดีที่สุด
  -> กรอกอัตราจ่ายที่เหมาะสมของสารแต่ละชนิด
  -> ระบบคำนวณต้นทุนสรุป
  -> ยืนยันปิดงาน
  -> ระบบล็อกการแก้ไข
```

## 6 สถานะเชิงตรรกะของงาน

ชื่อสถานะภายในฐานข้อมูลของระบบเดิมไม่ปรากฏบน UI เอกสารนี้จึงใช้ชื่อเชิงตรรกะเพื่ออธิบายพฤติกรรมเท่านั้น

| สถานะเชิงตรรกะ | สิ่งที่ผู้ใช้ทำได้ | เงื่อนไขไปสถานะถัดไป |
|---|---|---|
| Draft | แก้ข้อมูลหลัก เลือกกิจการและแหล่งน้ำ | บันทึกข้อมูลหลักสำเร็จ |
| Chemical Setup | เลือกสารและกรอกความเข้มข้น stock solution | ยืนยันเข้าสู่ขั้นอัตราจ่าย |
| Trial Setup | เพิ่มรอบและกรอก dose ของ 6 Jar | บันทึกรอบสำเร็จ |
| Result Entry | กรอกผลคุณภาพน้ำของ 6 Jar | บันทึกผลสำเร็จ |
| Summary | ยืนยัน Jar ที่ดีที่สุดและกรอก PPM ที่เหมาะสม | บันทึกสรุปสำเร็จ |
| Completed | อ่านข้อมูลได้ ปุ่มแก้ไขและปิดงานถูก disabled | สิ้นสุด flow |

**ข้อสังเกตของระบบเดิม:** สถานะที่แสดงในคอลัมน์รายการ เช่น `สถานะปกติ` ไม่ได้แสดงว่า workflow เสร็จหรือยัง จึงต้องถือว่าสถานะงานกับสถานะที่แสดงในตารางเป็นคนละแนวคิดจนกว่าจะยืนยัน schema เดิม

## 7 ข้อกำหนดหน้ารายการ Jar Test

### 7.1 โครงสร้างหน้าจอ

หน้ารายการอยู่ที่ `/umwwebapp/jartest` และแสดงหัวข้อ `Jar-Test` พร้อมปุ่มข้อมูล ปุ่มเปิดตัวกรอง และปุ่ม `Add`

ตารางต้องมีคอลัมน์ตามลำดับต่อไปนี้

1. ลำดับ
2. วันที่ทดสอบ Jar-Test
3. วันที่วัดคุณภาพน้ำ
4. กิจการประปา
5. แหล่งน้ำ
6. ประเภทน้ำ
7. สถานะ
8. คำสั่งดูและลบ

แต่ละแถวมีปุ่มดูรายละเอียดรูปตาและปุ่มลบรูปถังขยะ การดูรายละเอียดนำไปยัง URL รูปแบบ `/umwwebapp/jartest/action?id={jarTestId}`

### 7.2 ตัวกรอง

เมื่อเปิดส่วนค้นหา ต้องแสดงฟิลด์ต่อไปนี้

| ฟิลด์ | ประเภท | พฤติกรรม |

| กิจการประปา | Dropdown | ค่าเริ่มต้นเป็นกิจการตาม context ของผู้ใช้หรือระบบ |
| แหล่งน้ำ | Dropdown | มีค่า `ทั้งหมด` และรายการขึ้นกับกิจการที่เลือก |
| สถานะ | Dropdown | มีค่า `ทั้งหมด` |
| วันที่ | Date input | วันที่เริ่มต้น |
| ถึง | Date input | วันที่สิ้นสุด |
| ค้นหา | Button | ใช้ค่าตัวกรองทั้งหมดเพื่อโหลดรายการใหม่ |

รูปแบบวันที่ที่พบคือ `D/MM/BBBB` โดยแสดงปีพุทธศักราช เช่น `6/09/2569`

### 7.3 ผลลัพธ์ว่าง

## 8 ข้อกำหนดการสร้างข้อมูลหลัก

### 8.1 Modal Create

การกด `Add` เปิด modal ชื่อ `Create` โดยไม่เปลี่ยน route วันที่เริ่มทดสอบไม่ปรากฏเป็นช่องกรอกใน modal และระบบกำหนดวันที่ให้เมื่อบันทึก

ฟิลด์ส่วนข้อมูลทั่วไปมีดังนี้

| ฟิลด์ | ประเภท | พฤติกรรม |
|---|---|---|
| กิจการประปา | Dropdown | เลือกสถานีหรือกิจการ |
| แหล่งน้ำ | Dropdown | เปลี่ยนตามกิจการประปา |
| สถานะการเดินระบบ | Dropdown | เลือกหนึ่งค่า |

ตัวเลือกสถานะการเดินระบบที่ยืนยันได้

- ไม่ระบุ
- ตามกำลังผลิต
- เกินกำลังผลิต
- ต่ำกว่ากำลังผลิต

ตัวอย่าง dependency ที่ยืนยันจากการทดสอบคือ เมื่อเลือก `สถานีผลิต Head Office` ระบบกำหนดแหล่งน้ำเป็น `น้ำดิบ, LPTHEP`

### 8.2 คุณสมบัติน้ำดิบ

Modal Create มี numeric input จำนวน 10 ช่อง

| ลำดับ | ชื่อฟิลด์บน UI | หน่วย |
|---|---|---|
| 1 | TURBIDITY | NTU |
| 2 | TOTAL ALKALINITY as CaCO3 | mg/l |
| 3 | TRUE COLOUR | Pt-Co |
| 4 | IRON | mg/l |
| 5 | pH | ไม่มีหน่วย |
| 6 | TOTAL MANGANESE | mg/l |
| 7 | CONDUCTIVITY | µS/cm |
| 8 | SOLUBLE MANGANESE | mg/l |
| 9 | TEMPERATURE | °C |
| 10 | อื่นๆ | ไม่ระบุ |

ค่าที่ไม่กรอกแสดงเป็น `-` ในหน้ารายละเอียดบางตำแหน่ง ส่วนการแสดงทศนิยมของค่าที่กรอกใช้ 3 ตำแหน่ง เช่น `20.000`

### 8.3 การบันทึก

- ปุ่ม `SAVE` บันทึกข้อมูลและปิด modal
- ปุ่ม `CANCEL` ปิด modal โดยไม่บันทึก
- เมื่อบันทึกสำเร็จ ระบบแสดงข้อความ `บันทึกเรียบร้อย`
- ข้อมูลใหม่ปรากฏในหน้ารายการตามวันที่ที่ระบบสร้างให้

## 9 ข้อกำหนดหน้ารายละเอียด

หน้ารายละเอียดมี breadcrumb หรือ link กลับหน้ารายการ หัวข้อ `Jar-Test` และแท็บ 5 แท็บ

1. ข้อมูลหลัก
2. สารเคมีที่เลือก
3. ความเข้มข้น (PPM) ที่ใช้
4. ผลการทดสอบคุณภาพน้ำ
5. สรุปผลการทดสอบ

### 9.1 แท็บข้อมูลหลัก

แท็บนี้แสดง

- วันที่เริ่มทำการทดสอบโดยประมาณ
- ชื่อกิจการประปา
- ประเภทหรือแหล่งน้ำดิบ
- สถานะการเดินระบบ
- เงื่อนไขการกวนผสมและการตกตะกอน
- คุณสมบัติน้ำดิบ
- อัตราจ่ายสารเคมีที่แนะนำ

### 9.2 เงื่อนไขการกวนผสมและการตกตะกอน

ระบบเดิมแสดง 6 ขั้นตอน ค่า default ที่พบมีดังนี้

| ขั้นตอน | ชื่อที่แสดง | เวลา | ความเร็ว |
|---|---|---:|---:|
| 1 | PRE-OXIDATION | 0 วินาที | 250 RPM |
| 2 | PRE-OXIDATION | 0 วินาที | 250 RPM |
| 3 | PRE-OXIDATION | 0 นาที | 70 RPM |
| 4 | PRE-OXIDATION | 0 นาที | 40 RPM |
| 5 | PRE-OXIDATION | 0 นาที | 25 RPM |
| 6 | PRE-OXIDATION | 0 นาที | ไม่พบค่าความเร็วบนหน้าที่สำรวจ |

ชื่อทั้ง 6 ขั้นตอนปรากฏเป็น `PRE-OXIDATION` เหมือนกันในระบบเดิม เอกสารนี้บันทึกตามที่แสดงจริงและไม่แก้ชื่อให้เอง

### 9.3 อัตราจ่ายสารเคมีที่แนะนำ

ระบบแสดงคำแนะนำอย่างน้อยสองรายการ

- ช่วง Pre-chlorine หน่วย `PPM as available chlorine`
- ช่วงด่างทับทิม หน่วย `PPM`

ตัวอย่างที่ยืนยันจากการทดสอบ

| ข้อมูลน้ำดิบตัวอย่าง | ผลแนะนำที่ระบบแสดง |
|---|---|
| TURBIDITY 20, ALKALINITY 100, TRUE COLOUR 30, IRON 1, pH 6.5, TOTAL Mn 0.5, CONDUCTIVITY 200, SOLUBLE Mn 0.2, TEMP 25 | Pre-chlorine 6 ถึง 8 PPM และด่างทับทิม 0.300 ถึง 0.400 PPM |
| ข้อมูลน้ำดิบส่วนใหญ่ไม่ถูกกรอก | ช่วงแนะนำทั้งสองรายการเป็น 0 ถึง 0 |

สูตรหรือ rule table ที่สร้างช่วงแนะนำยังไม่ปรากฏจาก UI และต้องยืนยันเพิ่ม ห้ามใช้ตัวอย่างข้างต้นเป็นสูตรทั่วไป

### 9.4 การแก้ไขข้อมูลหลัก

ก่อนเข้าสู่ขั้นที่ข้อมูลถูกล็อก ปุ่ม `แก้ไข` เปิด modal ที่มีฟิลด์กิจการประปา แหล่งน้ำ สถานะการเดินระบบ และคุณสมบัติน้ำดิบ 10 ช่องเหมือนขั้นสร้าง การแก้ไขเงื่อนไขการกวนทั้ง 6 ขั้นไม่พบใน modal ที่สำรวจ

## 10 ข้อกำหนดการเลือกสารเคมี

### 10.1 โครงสร้าง

แท็บ `สารเคมีที่เลือก` แสดงปุ่ม `เลือกสาร` ปุ่ม `ถัดไป` และข้อความเตือน

> กดปุ่มถัดไปแล้วจะไม่สามารถกลับมาแก้ไขข้อมูลนี้ได้อีก

Modal `สารเคมีที่ใช้ทดสอบ` มี 5 หมวด แต่ละหมวดเลือกสารได้สูงสุดหนึ่งรายการ และมี numeric input สำหรับความเข้มข้น ค่าเริ่มต้นของแต่ละหมวดคือ `ไม่ได้ใช้`

### 10.2 หมวดและตัวเลือกสาร

| หมวด | ตัวเลือกที่ยืนยันจากระบบเดิม |
|---|---|
| สารออกซิแดนท์ Pre Oxidants | ไม่ได้ใช้, คลอรีนชนิดแก๊ส, คลอรีนชนิดน้ำ, สารออกซิแดนท์อื่นๆ |
| สารสร้างตะกอน Coagulants | ไม่ได้ใช้, สารส้มชนิดก้อน, สารส้มชนิดน้ำ, PACl ชนิดผง, PACl ชนิดน้ำ, ปูนขาว, สารสร้างตะกอนอื่นๆ |
| สารช่วยสร้างตะกอน Coagulant Aids | ไม่ได้ใช้, พอลิเมอร์ชนิดประจุลบ, พอลิเมอร์ชนิดประจุบวก, สารช่วยสร้างตะกอนอื่นๆ |
| สารปรับเพิ่มลดค่า pH | ไม่ได้ใช้, โซดาแอช, โซดาไฟ, กรดเกลือ, สารปรับค่าพีเอชอื่นๆ |
| สารเคมีบำบัดเพิ่มพิเศษ | ไม่ได้ใช้, ด่างทับทิม, สารเคมีบำบัดพิเศษอื่นๆ |

### 10.3 ความหมายของฟิลด์ความเข้มข้น

ใน modal ป้ายกำกับที่พบคือ `ความเข้มข้นที่ใช้ทดสอบ (PPM)` แต่ตารางหลังบันทึกใช้หัวคอลัมน์ `ค่าความเข้มข้นใน stock solution` พฤติกรรมการคำนวณพิสูจน์ว่าค่านี้ถูกใช้เป็นความเข้มข้นของ stock solution ไม่ใช่ dose ของแต่ละ Jar

ระบบสำเนาที่ต้องการความเหมือนด้าน UI ควรรักษาป้ายกำกับเดิม แต่ implementation ต้องแยกแนวคิดต่อไปนี้ออกจากกัน

- `stock concentration` กรอกตอนเลือกสาร
- `target dose PPM` กรอกแยกสำหรับ Jar 1 ถึง Jar 6 ในแต่ละรอบ

### 10.4 ตารางสารที่เลือก

หลังบันทึก ระบบแสดงตารางที่มีคอลัมน์

1. ชนิดของสารเคมี
2. ค่าความเข้มข้นใน stock solution
3. ราคาต่อหน่วย บาทต่อกิโลกรัม

ราคาต่อหน่วยมาจากข้อมูลสารหรือ stock ของระบบและไม่ใช่ค่าคงที่ใน Jar Test ตัวอย่างราคาที่พบมีทั้ง 0, 5.8 และ 57.5 บาทต่อกิโลกรัม

### 10.5 การล็อกขั้นเลือกสาร

หลังเข้าสู่แท็บกำหนด PPM ปุ่มแก้ไขสารจะ disabled ในการทดสอบที่ทำกับระบบเดิม ข้อกำหนดขั้นต่ำคือปุ่ม `ถัดไป` ต้องยืนยันการจบขั้นเลือกสารและทำให้ไม่สามารถกลับไปเปลี่ยนสารหรือ stock concentration ได้

## 11 ข้อกำหนดรอบทดสอบและ Jar

### 11.1 การเพิ่มรอบ

แท็บ `ความเข้มข้น (PPM) ที่ใช้` มีปุ่ม `เพิ่มครั้งที่` Modal ของรอบแรกใช้ชื่อ `เพิ่มอัตราการจ่ายสารเคมีครั้งที่ 1`

Modal ต้องมี

- รายละเอียดของครั้งที่ N
- กลุ่มช่องกรอก dose สำหรับสารแต่ละชนิดที่เลือก
- Jar No.1 ถึง Jar No.6 สำหรับสารแต่ละชนิด
- ปุ่ม `SAVE` และ `CANCEL`

จำนวน Jar ต่อรอบเป็น 6 ใบแบบคงที่ในระบบเดิม หน้าจอใช้คำว่า `ครั้งที่ 1` หลายตำแหน่งซึ่งบ่งชี้ว่ารองรับหลายรอบ แต่ transition ไปครั้งที่ 2 และจำนวนรอบสูงสุดยังต้องยืนยันเพิ่ม

### 11.2 ข้อมูลที่ระบบแสดงหลังบันทึกรอบ

สำหรับสารแต่ละชนิด ระบบแสดง

- อัตราจ่าย PPM ของ Jar 1 ถึง Jar 6
- ปริมาณการใช้ ml ของ Jar 1 ถึง Jar 6
- ต้นทุนสาร บาทต่อ ลบ.ม. ของ Jar 1 ถึง Jar 6

ชื่อแถวต้นทุนที่พบอาจแสดงเป็น `ต้นทุนค่าสารออกซิแดนท์` แม้สารนั้นเป็น Coagulant จึงถือเป็นข้อความของระบบเดิม ไม่ใช่การจำแนกประเภทที่ถูกต้องสำหรับ implementation ภายใน

## 12 สูตรคำนวณ

### 12.1 หลักการเจือจาง

ระบบใช้หลัก `C1V1 = C2V2` และแสดงผลเป็นสูตรเชิงพฤติกรรมดังนี้

```text
ปริมาณสารละลายที่ใช้ ml
= target dose PPM × 1000 ÷ stock concentration
```

ตัวอย่างที่ยืนยันจากระบบ

| สาร | Stock concentration | Target dose | ผลปริมาณการใช้ |
|---|---:|---:|---:|
| คลอรีนชนิดน้ำ | 4 | 1 PPM | 250 ml |
| คลอรีนชนิดน้ำ | 4 | 6 PPM | 1500 ml |
| PACl ชนิดน้ำ | 10 | 5 PPM | 500 ml |
| PACl ชนิดน้ำ | 10 | 30 PPM | 3000 ml |
| สารส้มชนิดน้ำ | 10 | 5 PPM | 500 ml |

ตัวคูณ 1000 เป็นพฤติกรรมที่ต้องรักษาเพื่อให้ผลตรงระบบเดิม การตีความหน่วยเต็มของ `V2` ไม่ได้แสดงบน UI จึงไม่ควรเปลี่ยนตัวคูณจากสมมติฐานทางเคมีเพียงอย่างเดียว

### 12.2 ต้นทุนสารเคมีต่อปริมาตรน้ำ

```text
ต้นทุนสารชนิดหนึ่ง บาทต่อ ลบ.ม.
= target dose PPM × ราคาสาร บาทต่อกิโลกรัม ÷ 1000
```

ตัวอย่าง

```text
สารส้มชนิดน้ำ 5 PPM ราคา 5.8 บาทต่อกิโลกรัม
= 5 × 5.8 ÷ 1000
= 0.029 บาทต่อ ลบ.ม.
```

```text
สารส้มชนิดน้ำ 30 PPM ราคา 5.8 บาทต่อกิโลกรัม
= 30 × 5.8 ÷ 1000
= 0.174 บาทต่อ ลบ.ม.
```

### 12.3 ต้นทุนรวมของ Jar

```text
ต้นทุนรวมของ Jar j
= ผลรวมต้นทุนของสารทุกชนิดที่เลือกใน Jar j
```

หากราคาต่อหน่วยของสารเป็น 0 ระบบเดิมแสดงต้นทุนรายสารเป็นค่าว่างในบางตาราง และแสดงต้นทุนรวมเป็น `0.000` การทำสำเนาควรรักษาพฤติกรรมการคำนวณเป็นศูนย์ ส่วนการแสดงค่าว่างหรือศูนย์ต้องทำตามตำแหน่งของ UI เดิม

### 12.4 การปัดเศษและการแสดงผล

- ปริมาณสารละลายแสดง 2 ตำแหน่ง เช่น `250.00`
- ค่าคุณภาพน้ำแสดง 3 ตำแหน่ง เช่น `0.100`
- ต้นทุนรวมแสดง 3 ตำแหน่ง เช่น `0.174`
- ค่า PPM ในตารางอัตราจ่ายอาจแสดงเป็นจำนวนเต็มเมื่อผู้ใช้กรอกจำนวนเต็ม

วิธีปัดเศษภายในก่อนแสดงยังต้องยืนยันเพิ่ม Implementation ควรคำนวณด้วย precision เต็มและปัดเฉพาะชั้นแสดงผล

## 13 ข้อกำหนดผลการทดสอบคุณภาพน้ำ

### 13.1 การเปิดกรอกผล

แท็บ `ผลการทดสอบคุณภาพน้ำ` มีปุ่ม `กรอกผลทดสอบ` ปุ่มนี้ disabled จนกว่าจะมีรอบอัตราจ่ายที่บันทึกแล้ว

Modal ใช้ชื่อ `ผลการทดสอบคุณภาพน้ำครั้งที่ N` และมี numeric input Jar 1 ถึง Jar 6 สำหรับค่าต่อไปนี้

#### หลังผ่านการตกตะกอน

1. ค่าความขุ่น NTU
2. ค่าสีจริง True Color หน่วย Pt-Co
3. ค่า pH

#### หลังผ่านการตกตะกอนและกรองด้วยกระดาษกรอง Whatman No 1 ขนาด 11 µm

4. สีปรากฏ Appearance Color หน่วย Pt-Co
5. ปริมาณแมงกานีสรวม Total Manganese

### 13.2 การประเมินผ่านหรือไม่ผ่าน

ระบบคำนวณสถานะของ Jar แต่ละใบอัตโนมัติ ผู้ใช้ไม่มีช่องเลือกสถานะผ่านหรือไม่ผ่าน

หลักการที่เจ้าของระบบยืนยันคือแต่ละพารามิเตอร์มี Bound ระบบต้องเปรียบเทียบค่าผลทดสอบกับ Bound ที่เกี่ยวข้อง และสรุปผลระดับ Jar ตามตรรกะต่อไปนี้

```text
result(parameter) = ผ่าน เมื่อค่าอยู่ใน Bound ของ parameter
jar_result = ผ่าน เมื่อทุก parameter ที่บังคับตรวจผ่าน
jar_result = ไม่ผ่าน เมื่อมีอย่างน้อยหนึ่ง parameter ไม่ผ่าน
```

ชุดทดสอบที่ใช้ยืนยันพฤติกรรม

| Jar | Turbidity | True Color | pH | Appearance Color | Total Mn | ผลระบบ |
|---:|---:|---:|---:|---:|---:|---|
| 1 | 100 | 100 | 3 | 100 | 10 | ไม่ผ่าน |
| 2 | 10 | 20 | 5 | 20 | 1 | ไม่ผ่าน |
| 3 | 5 | 10 | 6 | 10 | 0.5 | ไม่ผ่าน |
| 4 | 1 | 5 | 7 | 5 | 0.1 | ผ่าน |
| 5 | 0.5 | 2 | 8 | 2 | 0.01 | ผ่าน |
| 6 | 0.1 | 1 | 11 | 1 | 0.001 | ผ่าน |

ตารางนี้พิสูจน์ว่าระบบใช้ Bound แต่ไม่สามารถใช้หา Bound รายพารามิเตอร์ได้ เพราะแต่ละ Jar เปลี่ยนหลายตัวแปรพร้อมกัน โดยเฉพาะ pH 11 ใน Jar 6 ยังถูกจัดว่าผ่าน จึงห้ามสมมติช่วงมาตรฐานน้ำทั่วไปแทนค่าที่ระบบเดิมใช้

### 13.3 ตารางผลลัพธ์

หลังบันทึก ระบบแสดง

- ค่าผลทั้ง 5 พารามิเตอร์ของ Jar 1 ถึง Jar 6
- แถวสรุปผลการบำบัดน้ำดิบแต่ละ Jar เป็น `ผ่าน` หรือ `ไม่ผ่าน`
- ต้นทุนค่าสารเคมีรวมของ Jar 1 ถึง Jar 6

## 14 ข้อกำหนดสรุปผล

### 14.1 หน้าสรุป

แท็บ `สรุปผลการทดสอบ` มีหัวข้อ `สรุปผลการทดสอบครั้งที่ N` และแสดง

- ปุ่ม `เลือก Jar ที่ดีที่สุด`
- อัตราจ่ายที่เหมาะสมของสารแต่ละชนิด หน่วย PPM
- ต้นทุนค่าสารเคมีรวมโดยประมาณ หน่วยบาทต่อ ลบ.ม.
- ปุ่ม `กรอกสรุปผลทดสอบ`
- ปุ่ม `เสร็จงาน`

### 14.2 การเลือก Jar ที่ดีที่สุด

เมื่อกด `เลือก Jar ที่ดีที่สุด` ระบบเปิด modal ยืนยันด้วยข้อความ

> คุณต้องการเลือก Jar นี่เป็นข้อมูลที่ดีที่สุดใช่หรือไม่ ?

และมีปุ่ม `NO` กับ `YES`

จากการทดสอบ การกด `YES` ทำให้ปุ่มเลือก Jar หายไปและแสดงข้อความบันทึกสำเร็จ แต่ไม่ได้เติม PPM ที่เหมาะสมให้ในตารางโดยอัตโนมัติ พฤติกรรมนี้ต้องรักษาไว้ใน baseline จนกว่าจะมีหลักฐานเพิ่มเติมว่าการเลือกจากบริบทอื่นทำงานต่างกัน

### 14.3 การกรอกสรุป

ปุ่ม `กรอกสรุปผลทดสอบ` เปิด modal ที่มี numeric input `กรอกค่าที่เหมาะสม` หนึ่งช่องต่อสารเคมีที่เลือก ผู้ใช้ต้องกรอก PPM สรุปเอง

เมื่อบันทึก ระบบแสดง PPM ที่เหมาะสมของสารแต่ละชนิดและคำนวณต้นทุนรวมด้วยสูตรต้นทุนในหัวข้อ 12

### 14.4 การปิดงาน

ปุ่ม `เสร็จงาน` เปิด modal `ยืนยัน` พร้อมข้อความ

> คุณต้องการปิดงานของอัตราการจ่ายสารเคมีครั้งถัดไป?

เมื่อกด `YES`

- ระบบบันทึกสำเร็จ
- ปุ่ม `เสร็จงาน` ถูก disabled
- ปุ่ม `กรอกสรุปผลทดสอบ` ถูก disabled
- ข้อมูลของงานเข้าสู่สภาพอ่านอย่างเดียวในส่วนที่ทดสอบ

## 16 ข้อกำหนด UI และ Interaction

### 16.1 Desktop

- ใช้ sidebar ด้านซ้ายและ content area ด้านขวา
- ตารางใช้หัวคอลัมน์และแถวข้อมูลแบบ grid
- ฟอร์มสร้าง แก้ไข เลือกสาร เพิ่มรอบ กรอกผล และสรุป ใช้ modal
- การบันทึกไม่เปลี่ยนหน้าใน modal flow แต่ปรับข้อมูลส่วนปัจจุบันและแสดง toast
- ปุ่มที่ยังใช้ไม่ได้ต้องแสดง disabled state อย่างชัดเจน

### 16.2 Mobile

- ที่ viewport ประมาณ 390 x 844 sidebar เปลี่ยนเป็นเมนูแบบ hamburger
- ตารางที่กว้างกว่าหน้าจอต้องอยู่ในพื้นที่เลื่อนแนวนอน
- Modal และ form ต้องย่อให้ใช้งานบนจอแคบได้โดยไม่ตัดปุ่มสำคัญ
- ลำดับแท็บ ฟิลด์ และปุ่มต้องเหมือน desktop

### 16.3 ข้อความตอบกลับ

- เมื่อบันทึกสำเร็จใช้ข้อความ `บันทึกเรียบร้อย`
- ขั้นปิดงานและเลือก Jar ที่ดีที่สุดต้องมี confirmation modal
- ปุ่ม `CANCEL` หรือ `NO` ต้องไม่บันทึกการเปลี่ยนแปลง
- ปุ่มลบต้องถือเป็น destructive action แม้ confirmation เดิมยังไม่ถูกสำรวจ

## 17 ข้อกำหนดข้อมูลเชิงแนวคิด

ส่วนนี้เป็น conceptual model สำหรับสื่อสารความสัมพันธ์ของระบบเดิม ไม่ใช่ข้อเสนอ database schema สำหรับระบบอัปเกรด

```text
JarTest
  1 -> 1 Station or Waterworks
  1 -> 1 WaterSource
  1 -> 1 OperatingStatus
  1 -> 1 RawWaterProfile
  1 -> many MixingConditions
  1 -> many SelectedChemicals
  1 -> many TestRounds

SelectedChemical
  many -> 1 ChemicalMaster or ChemicalStock
  has stockConcentration
  has unitPriceSnapshot or unitPriceReference

TestRound
  1 -> 6 Jars
  1 -> many ChemicalDoses
  1 -> many JarQualityResults
  1 -> 1 RoundSummary

ChemicalDose
  belongs to TestRound, Jar and SelectedChemical
  has targetDosePpm
  has calculatedSolutionVolumeMl
  has calculatedCostBahtPerM3

JarQualityResult
  belongs to TestRound and Jar
  has turbidity, trueColor, pH, appearanceColor, totalManganese
  has calculatedPassFail

RoundSummary
  identifies the confirmed best round or Jar context
  has recommendedPpmByChemical
  has calculatedTotalCostBahtPerM3
```

Bound และสูตรอัตราจ่ายแนะนำมีอยู่ในตรรกะระบบเดิม แต่ตำแหน่งจัดเก็บและโครงสร้างข้อมูลยังไม่ทราบ จึงไม่กำหนดเป็น schema ใน baseline นี้

## 19 Validation Requirements

พฤติกรรมที่ยืนยันได้คือช่องคุณภาพน้ำ ความเข้มข้น และ PPM เป็น numeric input อย่างไรก็ตาม ยังไม่ได้ยืนยันข้อจำกัดระดับ field เช่น ค่าติดลบ จำนวนทศนิยมสูงสุด ค่าว่าง ค่าสูงสุด และข้อความ error

ข้อกำหนดสำหรับ baseline implementation มีดังนี้

- ต้องไม่รับข้อความที่ไม่ใช่ตัวเลขใน numeric field
- ต้องรักษาค่าทศนิยมโดยไม่ปัดระหว่างการคำนวณ
- ต้องปัดเฉพาะตอนแสดงผล
- ต้องไม่หารด้วยศูนย์เมื่อ stock concentration เป็น 0 หรือว่าง
- ต้องไม่คำนวณ dose สำหรับหมวดที่เลือก `ไม่ได้ใช้`
- ต้องไม่เปิดกรอกผลก่อนบันทึกรอบ
- ต้องไม่เปิดสรุปผลก่อนมีผลทดสอบ
- ต้องไม่อนุญาตให้แก้ไขผ่าน UI หลังปิดงาน

กฎว่าค่า 0 หรือค่าว่างใช้ได้ในแต่ละฟิลด์หรือไม่ต้องยืนยันกับระบบเดิมก่อนกำหนด acceptance criteria แบบบังคับ

## 20 Acceptance Test Scenarios

### AT-001 สร้างงานพื้นฐาน

1. เปิดหน้ารายการ
2. กด Add
3. เลือกกิจการและแหล่งน้ำ
4. กรอกสถานะการเดินระบบและคุณสมบัติน้ำดิบ
5. กด SAVE

ผลที่คาดหวังคือ modal ปิด แสดง `บันทึกเรียบร้อย` และพบรายการใหม่ในตารางตามตัวกรองที่เกี่ยวข้อง

### AT-002 ตรวจ dependency ของสถานีและแหล่งน้ำ

เลือก `สถานีผลิต Head Office`

ผลที่คาดหวังคือแหล่งน้ำเปลี่ยนเป็นรายการของ Head Office และในการทดสอบปัจจุบันแสดง `น้ำดิบ, LPTHEP`

### AT-003 เลือกสารหลายหมวด

เลือกคลอรีนชนิดน้ำจาก Pre Oxidants และ PACl ชนิดน้ำจาก Coagulants แล้วกำหนด stock concentration

ผลที่คาดหวังคือตารางแสดงสารทั้งสองชนิด ความเข้มข้น และราคาต่อหน่วยแยกกัน

### AT-004 ตรวจสูตรปริมาณสารละลาย

กำหนดคลอรีน stock concentration 4 และ target dose 1 ถึง 6 PPM

ผลที่คาดหวังคือปริมาณสารละลายเท่ากับ 250, 500, 750, 1000, 1250 และ 1500 ml

### AT-005 ตรวจสูตรต้นทุน

กำหนดสารราคา 5.8 บาทต่อกิโลกรัมและ target dose 5 PPM

ผลที่คาดหวังคือต้นทุนเท่ากับ 0.029 บาทต่อ ลบ.ม.

### AT-006 ตรวจกรณีราคาเป็นศูนย์

เลือกสารที่ราคาต่อหน่วยเป็น 0 และกำหนด target dose มากกว่า 0

ผลที่คาดหวังคือต้นทุนรวมของ Jar เท่ากับ 0.000

### AT-007 ตรวจ Bound

กรอกค่าผลของ Jar ให้มีอย่างน้อยหนึ่งค่าหลุด Bound และกรอกอีก Jar ให้ทุกค่าอยู่ใน Bound

ผลที่คาดหวังคือ Jar แรกเป็น `ไม่ผ่าน` และ Jar หลังเป็น `ผ่าน` โดยไม่มีช่องให้ผู้ใช้เลือกสถานะเอง

### AT-008 ตรวจสรุปสารหลายชนิด

กรอก PPM ที่เหมาะสมหนึ่งค่าต่อสารใน modal สรุป

ผลที่คาดหวังคือหน้าสรุปแสดงค่าแยกต่อสารและต้นทุนรวมตามสูตร

### AT-009 ตรวจการล็อกหลังปิดงาน

บันทึกสรุปแล้วกด `เสร็จงาน` และยืนยัน `YES`

ผลที่คาดหวังคือแสดง `บันทึกเรียบร้อย` ปุ่มเสร็จงานและกรอกสรุปถูก disabled และไม่สามารถแก้ไขงานผ่าน flow ปกติได้

### AT-010 ตรวจ mobile

เปิดหน้ารายการและรายละเอียดที่ viewport ประมาณ 390 x 844

ผลที่คาดหวังคือ sidebar ใช้ hamburger ตารางเลื่อนแนวนอนได้ และ modal ยังเข้าถึงทุกฟิลด์กับปุ่มบันทึกได้

## 21 พฤติกรรมที่ต้องรักษาแม้ดูไม่สมบูรณ์

รายการต่อไปนี้เป็นพฤติกรรมหรือข้อความที่พบในระบบเดิม การสร้าง baseline ต้องไม่แก้เองโดยไม่มี requirement รุ่นอัปเกรด

- ชื่อเมนูและแท็บใช้ทั้งภาษาไทยและอังกฤษ
- ป้ายใน modal เลือกสารระบุ `ความเข้มข้นที่ใช้ทดสอบ (PPM)` แต่ตารางเรียกว่า stock solution
- ชื่อแถวต้นทุนอาจระบุสารออกซิแดนท์แม้แถวนั้นเป็นสารหมวดอื่น
- ขั้นตอนกวนทั้ง 6 ขั้นแสดงชื่อ PRE-OXIDATION เหมือนกัน
- ข้อความ confirmation ปิดงานใช้ถ้อยคำ `อัตราการจ่ายสารเคมีครั้งถัดไป`
- ปุ่มเลือก Jar ที่ดีที่สุดไม่เติม PPM สรุปให้อัตโนมัติในการทดสอบที่ทำ
- ค่า 0 ของราคาต่อหน่วยอาจแสดงต้นทุนรายสารเป็นช่องว่าง แต่ต้นทุนรวมเป็น 0.000

## 22 รายการที่ต้องยืนยันจากระบบเดิมเพิ่ม

รายการนี้เป็นช่องว่างของความรู้เกี่ยวกับระบบเดิม ไม่ใช่รายการฟังก์ชันอัปเกรด

1. ค่า Bound จริงของ Turbidity, True Color, pH, Appearance Color และ Total Manganese
2. การใช้ inclusive หรือ exclusive comparison ที่ขอบ Bound
3. พารามิเตอร์ใดมีทั้ง lower และ upper Bound หรือมีเฉพาะด้านเดียว
4. สูตรหรือ rule table สำหรับช่วง Pre-chlorine และด่างทับทิมที่แนะนำ
5. หน่วยเต็มและ reference volume ที่ตัวคูณ 1000 ในสูตร C1V1 เท่ากับ C2V2 อ้างอิง
6. วิธีปัดเศษภายในก่อนแสดงผล
7. จำนวนรอบทดสอบสูงสุดและ transition จากครั้งที่ 1 ไปครั้งถัดไป
8. ผลของการกด `เลือก Jar ที่ดีที่สุด` ในกรณีมีหลายรอบ
9. validation ของค่าติดลบ ค่า 0 ค่าว่าง และจำนวนทศนิยม
10. เงื่อนไขและ confirmation ของการลบรายการ
11. สิทธิ์ของ role แต่ละประเภท
12. ความหมายและที่มาของคอลัมน์ `วันที่วัดคุณภาพน้ำ`
13. ความหมายของ `สถานะปกติ` ในหน้ารายการและความสัมพันธ์กับ workflow status
14. วิธีแก้ไขเงื่อนไขการกวนทั้ง 6 ขั้น หากระบบเดิมรองรับ

## 23 Definition of Done สำหรับการสร้าง Baseline

การสร้างโมดูล Jar Test ดั้งเดิมถือว่าเสร็จเมื่อ

- หน้ารายการ ตัวกรอง ตาราง และ action ทำงานตามหัวข้อ 7
- Create และ Edit ครบทุกฟิลด์ตามหัวข้อ 8 และ 9
- มีแท็บ 5 แท็บตามลำดับเดิม
- ตัวเลือกสารครบทั้ง 5 หมวด
- สร้างรอบ 6 Jar และสารหลายชนิดได้
- ผลปริมาณสารและต้นทุนตรงตัวอย่างทดสอบ
- กรอกผลคุณภาพน้ำและประเมิน Bound ได้
- สรุป PPM แยกตามสารและคำนวณต้นทุนรวมได้
- confirmation และการล็อกหลังปิดงานทำงาน
- responsive behavior ใช้งานได้บน desktop และ mobile
- ไม่มีฟังก์ชันอัปเกรดที่ยังไม่ได้อนุมัติปะปนอยู่ใน baseline
- รายการที่ยังไม่ทราบในหัวข้อ 22 ถูกเก็บเป็นค่าหรือ task ที่ติดป้ายชัดเจน ไม่ถูกแทนด้วยการคาดเดา

## 24 คำสั่งย่อสำหรับส่งต่อ AI ผู้พัฒนา

ให้นำเอกสารนี้ไปสร้างโมดูล Jar Test ที่เลียนแบบระบบ Utilities Mobile Workflow เวอร์ชัน 1.6.16 เฉพาะพฤติกรรมเดิม Implement หน้ารายการ Create Detail 5 Tabs การเลือกสาร 5 หมวด รอบทดสอบ 6 Jar สูตร C1V1 เท่ากับ C2V2 สูตรต้นทุน การกรอกผล การตรวจ Bound การสรุปผล และการปิดงานตามข้อกำหนดทุกข้อ ห้ามเพิ่มฟังก์ชันอัปเกรด ห้ามแต่งค่า Bound หรือสูตรแนะนำสารเคมีที่ยังไม่ทราบ และต้องแยกค่าที่รอยืนยันออกจาก business logic หลักเพื่อให้เติมข้อมูลจริงภายหลังได้
