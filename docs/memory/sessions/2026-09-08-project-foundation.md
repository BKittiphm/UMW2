# บันทึกการคุย: Jar Test, Global Master และการส่งต่องาน

> สถานะการอ่าน: ความเข้าใจเรื่อง Water Source ในบันทึกนี้ถูกปรับภายหลัง โปรดอ่าน [คำชี้แจงวันที่ 9 กันยายน](2026-09-09-water-quality-source-structure.md) ก่อนนำไปออกแบบ

วันที่จัดทำ: 2026-09-08 เป็นวันที่รวบรวม ไม่ใช่เวลาที่ทุกข้อความเกิดขึ้น

ประเภท: สรุปย้อนหลังจากข้อความผู้ใช้ที่ปรากฏในบริบทปัจจุบัน คำตอบก่อนหน้า และเอกสารใน repository ไม่ใช่ transcript เต็ม ไม่มีการสำรวจเว็บหรือทดสอบ Jar Test ใหม่ระหว่างจัดทำบันทึกนี้

## เป้าหมายและลำดับความคิด

ผู้ใช้เริ่มจากการต้องการเข้าใจเว็บเดิมเพื่อสร้างแอปอ้างอิง โดยให้สำรวจ Jar Test ให้ครบก่อน รวมถึงการคำนวณ จากนั้นขอเอกสารที่ส่งให้ AI อื่นใช้ได้ ผู้ใช้ระบุว่ากำลังคิดและออกแบบ schema สำหรับการอัปเกรดอยู่ จึงต้องเก็บพฤติกรรมดั้งเดิมเป็นหลักฐานแยกไว้

ต่อมาผู้ใช้ชี้แจงว่าเป้าหมายคือทั้งแอป แต่จะเริ่มจากฟังก์ชันใหญ่ Jar Test แล้วทยอยเพิ่มงานอื่น มี Global Master ใช้ร่วมกันแน่นอน ผู้ใช้ยอมรับให้เตรียมหลายองค์กร แม้ปัจจุบันตั้งใจใช้ภายในองค์กรเดียว เพื่อรองรับอนาคต

ผู้ใช้ต้องการย้ายเครื่องและเปลี่ยน AI โดยคงความเข้าใจ จึงอนุญาตให้สร้างเอกสารส่งต่อ ระบุ repository ปลายทาง และขอเพิ่มบันทึกความจำของโครงการ

## คำยืนยันจากผู้ใช้และการแก้ความเข้าใจ

| เรื่อง | ข้อความ/ความหมายที่ผู้ใช้ยืนยัน | ผลต่อการทำงาน |
| --- | --- | --- |
| ทดลองระบบเดิม | ให้เลือกกิจการประปา/ตัวเลือกสถานีผลิต Head Office เพราะใช้ทดสอบ | ใช้เฉพาะพื้นที่ทดสอบที่ระบุในการบันทึก ไม่ลบข้อมูลจริง |
| การผ่าน/ไม่ผ่าน | เกณฑ์ถูกตั้งเป็น Bound | ต้องหาค่า Bound จริง ห้ามแทนด้วยค่ามาตรฐานที่เดา |
| ขอบเขตเอกสารเดิม | ขอเฉพาะ Jar Test ดั้งเดิมทั้งหมดก่อน ส่วนอัปเกรดค่อยคุย | เก็บ legacy specification แยกจาก target model |
| ลำดับพัฒนา | ทำทั้งแอป เริ่ม Jar Test ทีละฟังก์ชันใหญ่ | ยังไม่กำหนดรายละเอียดโมดูลถัดไป |
| หลายองค์กร | รองรับหลายองค์กรเผื่ออนาคต | เก็บ Organization เป็นขอบเขตที่ต้องรองรับ |
| Business Unit | กิจการประปาเป็นคนละระดับกับสถานี และมีได้หลายสถานี | ห้ามรวม Business Unit กับ Site |
| Site | สถานีอยู่ภายใต้กิจการประปา และให้ตัดคำว่าผลิตออก | ใช้ชื่อ canonical ว่าสถานี |
| Water Source | แหล่งน้ำหนึ่งแหล่งใช้ร่วมหลาย Site ได้ และเป็น Global Master | เก็บความสัมพันธ์การใช้แหล่งน้ำของแต่ละ Site |
| Site–Water Source | แหล่งน้ำที่เลือกมีผูกไว้กับ Site ว่าที่ไหนใช้อันไหน | รายการที่เลือกต้องสอดคล้องกับ Site |

คำว่า Global Master ยังไม่ยืนยันว่าแชร์ข้อมูลข้าม Organization ได้หรือไม่ คำตอบก่อนหน้าของ AI ที่ใช้คำว่า “ระดับระบบ/Organization” คลุมเครือ จึงไม่ใช้เป็นการอนุมัติขอบเขตข้อมูล

## สูตรและหลักฐานจากการสำรวจเดิม

ผู้ใช้ถามว่าคำนวณด้วย C1V1 = C2V2 ใช่หรือไม่ เอกสาร legacy บันทึกพฤติกรรม `solution_ml = target_dose_ppm * 1000 / stock_concentration` และต้นทุน `dose_ppm * unit_price / 1000` หลักฐานตัวอย่างและรายละเอียดอยู่ใน [legacy specification](../../../JarTest/legacy-jar-test-product-functional-spec-th.md) หัวข้อ 12 และ 20

ต้องแยกสูตรเชิงพฤติกรรมที่สังเกตได้ออกจากความเข้าใจหน่วยทางกายภาพ: หน่วยเต็มและ reference volume ของตัวคูณ 1000 ยังเป็นข้อที่ต้องยืนยัน ค่า Bound จริง ขอบแบบรวม/ไม่รวม และสูตรคำแนะนำสารเคมียังไม่ครบ ห้ามสรุปว่าเข้าใจ logic ทั้งหมดแล้ว

สถานะการสำรวจและการทดสอบที่บันทึกไว้เป็นข้อมูลจากงานก่อนหน้า ไม่ใช่ผลทดสอบซ้ำในช่วงสร้างความจำนี้

## ข้อเสนอของ AI ที่ยังไม่ใช่ข้อกำหนดอนุมัติ

- Modular monolith เป็นแนวทางที่เคยเสนอ ยังไม่ได้เลือก technology stack หรือรูปแบบ deployment
- การให้ Jar Test อ้าง `site_water_source_id` โดยตรงเป็นข้อเสนอ ยังเลือกใช้คู่คีย์พร้อม constraint ได้ในขั้นออกแบบ schema
- ราคา/ชื่อ/Bound แบบ snapshot, effective dates, default source และ active status ยังไม่ตกลง
- การแชร์ Water Source ข้าม Business Unit และข้าม Organization ยังเปิดอยู่
- การทำฟังก์ชันตั้งค่า Bound หรืออัปเกรด UX ต้องคุย requirement เพิ่ม

เหตุผลเชิงออกแบบที่ AI เสนอ: ความสัมพันธ์หลายต่อหลายช่วยไม่ให้ต้องทำสำเนาแหล่งน้ำต่อ Site และการแยก Business Unit/Site ช่วยไม่ให้ป้ายใน UI เก่าทำให้ schema ใหม่รวมคนละระดับ เหตุผลเหล่านี้เป็นคำอธิบายประกอบข้อยืนยันของผู้ใช้
