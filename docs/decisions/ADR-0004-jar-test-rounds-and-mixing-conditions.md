# ADR-0004: Jar Test rounds and mixing conditions

- Status: Accepted; amended 2026-09-30
- Date: 2026-09-25; amended 2026-09-30 (sequential rounds; fixed mixing steps and optional values)
- Scope: Jar Test transaction model in UMW2

## Context

UMW เดิมมีการทดลองเป็นรอบ โดยแต่ละรอบมี Jar 1–6 ส่วนร่าง Transaction ก่อนหน้านี้ให้บีกเกอร์อ้างงานตรง จึงแยกรอบหลายรอบไม่ได้ สภาวะกวนและตกตะกอนเป็นข้อมูลของแต่ละการทดลอง; สำหรับ UMW2 เจ้าของโครงการยืนยันว่าขั้นมาตรฐานมี 5 ขั้นและเหมือนกันทุก Site

## Decision

1. หนึ่งงาน `jar_tests` มีหลาย `jar_test_rounds`; `round_no` ไม่ซ้ำภายในงาน
2. `jar_test_beakers` อ้างรอบ และ `beaker_no` อยู่ในช่วง 1–6 โดยไม่ซ้ำในรอบ ผู้ใช้เลือกจำนวน Jar ที่จะทดสอบได้ ไม่จำเป็นต้องใช้ครบ 6
3. `jar_test_mixing_conditions` อ้างรอบและเก็บค่าการทดลองภายใต้ 5 ขั้นมาตรฐานตามลำดับเดียวกันทุก Site: PRE-OXIDATION, COAGULATION, FLOCCULATION S1, FLOCCULATION S2 และ SEDIMENTATION; ระยะเวลาเป็นวินาที และหน้าจออ้างอิงแสดง RPM เฉพาะ 4 ขั้นแรก
4. `jar_tests.site_raw_unit_id` อ้างรายการ `site_raw_units` ที่เปิดใช้งานและมี `site_id` ตรงกับงาน ระบบตรวจทั้งตอนเลือกและตอนบันทึก
5. ผลคุณภาพน้ำวัดในวันเดียวกับวันทดสอบที่ระบุโดย `jar_tests.test_datetime`; ไม่เพิ่มฟิลด์วัน/เวลาวัดแยกหรือ `operating_status_id` ข้อนี้ไม่อ้างว่าเวลาของทุกการวัดตรงกับเวลาเริ่มทดสอบ
6. สภาวะกวนและตกตะกอนเป็นข้อมูลบันทึกการทดลอง ไม่ใช้คำนวณ dose หรือผ่าน/ไม่ผ่านในขอบเขตปัจจุบัน
7. งานใหม่เริ่มต้นด้วยหนึ่งรอบ ผู้ใช้เพิ่มรอบได้
8. ผู้ใช้กดเข้า Jar ที่เลือกเพื่อกรอกผล ก่อน submit ต้องมีผลครบทุก Jar ที่เลือกในทุกรอบ; Jar ที่ไม่ได้เลือกไม่ถูกนำมาตรวจความครบถ้วน
9. การแนะนำ Jar ที่ดีที่สุดเป็นระดับงาน โดยนำ Jar ที่ผ่านเกณฑ์จากทุกรอบมาเปรียบเทียบร่วมกันและแนะนำ Jar ที่มีต้นทุนสารเคมีรวมต่ำสุด; dose สรุปสุดท้ายยังแยกเก็บและอาจต่างจาก dose ของ Jar ที่แนะนำ
10. รอบใหม่เป็นการทดลองต่อจากรอบก่อน ผู้ใช้เริ่มรอบถัดไปเมื่อต้องการโดยกด “เพิ่มรอบ”; ระบบไม่สร้างหลายรอบรอไว้ล่วงหน้า
11. ผู้ใช้เพิ่มรอบถัดไปได้เมื่อผลคุณภาพของ Jar ทุกใบที่เลือกในรอบก่อนหน้าครบตามพารามิเตอร์ผลทดสอบที่ active; Jar ที่ไม่ได้เลือกไม่นับว่าขาดผล
12. สภาวะของทั้ง 5 ขั้นเป็น optional: ช่องที่ยังไม่กรอกอาจแสดง `0` เป็น placeholder แต่ไม่ถือเป็นค่าข้อมูลและต้องบันทึกเป็น `NULL`; เมื่อแสดงค่าที่ไม่มีให้แสดง “ไม่ได้ระบุ”. การเว้นค่าสภาวะไม่ขัดขวางการบันทึกผลหรือเพิ่มรอบ และค่าดังกล่าวไม่ใช้คำนวณ dose หรือ pass/fail. ชุดขั้นไม่ต้องมีการตั้งค่าหรือ mapping ราย Site; วิธีแทน stage code ใน physical schema ยังเป็นการออกแบบแยก

## Consequences

- ผลน้ำดิบยังอยู่ระดับงาน ส่วน dose และผลคุณภาพอยู่ใต้บีกเกอร์ของแต่ละรอบ
- UI ต้องแยกสถานะ Jar ที่เลือก/ยังกรอกไม่ครบ/กรอกครบ เพื่อป้องกัน submit งานที่ผลไม่ครบ
- บีกเกอร์ที่แนะนำ/เลือกสรุปผลต้องย้อนผ่านรอบไปยังงานเดียวกัน; หากมี Jar ผ่านหลายรอบ ให้เปรียบเทียบต้นทุนรวมข้ามรอบก่อนแนะนำ
- การสร้างรอบถัดไปเป็นการกระทำตามต้องการของผู้ใช้ ไม่ใช่การสร้างรอบเปล่าหลายรอบตั้งแต่เริ่มงาน
- UI ต้องไม่อนุญาตให้เพิ่มรอบถัดไปจนกว่าผลของ Jar ที่เลือกในรอบก่อนหน้าจะครบ
- กติกาตัดสินเมื่อ Jar ที่ผ่านมีต้นทุนต่ำสุดเท่ากันยังไม่ได้กำหนด
- ทุก Site แสดงชุดขั้นกวนผสม/ตกตะกอนเดียวกัน; ค่าสภาวะที่ไม่มีเป็น `NULL` ไม่ใช่ตัวเลขศูนย์ และไม่เป็นเงื่อนไขบังคับของงาน
- การเลือกสารหนึ่งรายการต่อประเภทได้ข้อสรุปแล้วว่าล็อกระดับงาน ดู [ADR-0005](ADR-0005-jar-test-chemical-selection-per-job.md)
- เอกสารนี้กำหนดแบบร่างเชิงโดเมน; physical PostgreSQL DDL ยังต้องออกแบบและทบทวนต่างหาก

## Evidence

- คำยืนยันของเจ้าของโครงการวันที่ 25 กันยายน 2569
- คำยืนยันของเจ้าของโครงการวันที่ 30 กันยายน 2569 เรื่องการเปรียบเทียบ Jar ที่ผ่านข้ามทุกรอบและการเพิ่มรอบตามต้องการ
- คำยืนยันของเจ้าของโครงการวันที่ 30 กันยายน 2569 ให้กรอกผล Jar ที่เลือกในรอบก่อนหน้าให้ครบก่อนเพิ่มรอบถัดไป
- คำยืนยันของเจ้าของโครงการวันที่ 30 กันยายน 2569 ว่า 5 ขั้นเป็นมาตรฐานทุก Site, `0` เป็น placeholder แทนค่าว่าง, สามารถไม่กรอกได้ และค่าที่ไม่มีให้แสดง “ไม่ได้ระบุ”; ภาพหน้าจอ MAMIs ที่ผู้ใช้แนบแสดงชื่อและลำดับขั้น รวมถึง RPM ใน 4 ขั้นแรก
- [Legacy Jar Test baseline](../../JarTest/legacy-jar-test-product-functional-spec-th.md) หัวข้อ 11 และ 14
